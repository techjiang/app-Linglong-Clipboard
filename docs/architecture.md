# 架构说明

本文面向二次开发者，说明分层边界、关键数据流与几个刻意的设计取舍。
面向使用者的内容见 [README](../README.md)。

## 分层

```
        ┌─────────────────────────────────────────┐
        │  ui/          界面与交互，唯一依赖 Qt   │
        └────────────────┬────────────────────────┘
                         │ 只向下调用
        ┌────────────────▼────────────────────────┐
        │  core/        业务逻辑，零 Qt 依赖      │
        │               可脱离图形环境测试        │
        └────────────────┬────────────────────────┘
                         │
        ┌────────────────▼────────────────────────┐
        │  platform/    平台差异，接口 + 多实现   │
        └─────────────────────────────────────────┘
```

三条硬约束：

1. **`core/` 不导入 Qt。** 这是整个设计的地基。核心逻辑能在无显示器环境下跑测试，
   也让「换掉界面框架」变成局部改动。
2. **平台判断不出现在 `ui/` 和 `core/`。** 需要原生能力时调 `platform/` 的接口，
   由 `detect_backend()` 挑选实现。
3. **`ui/` 不直接读写数据库。** 界面通过信号把意图发给 `Application`，
   由控制器统一处理。这样「暂停采集」「退出清理」这类全局状态只有一处。

## 关键数据流

### 采集

```
系统剪贴板
   │
   │ ① ClipboardMonitor（守护线程，默认 300ms 轮询）
   │    · 用内容指纹比对，指纹未变直接返回
   ▼
   │ ② gui_invoke → 切回 GUI 线程读取
   │    QClipboard 只能在所属线程访问，跨线程读会拿到空数据
   │    顺带收下各种形式：text/html、text/plain 原始字节、Markdown、uri-list
   ▼
ClipboardItem（原始载荷）
   │
   │ ③ Collector.process()（仍在采集线程，不碰 Qt）
   │    · 补齐来源（FocusTracker，按秒缓存）
   │    · 处理形式（clipboard_formats）：补 html、Markdown 纠偏、写形式清单
   │    · 截图 OCR（OcrEngine）—— 识别结果写回 content
   │    · 类型识别 / 标签抽取（classify）
   │    · 隐私风控（PrivacyGuard）
   │    · 超长文本截断（capture.max_text_length）
   │    · 内容归一（normalize）后算指纹 —— 同一页面的不同渠道链接算同一条
   │    · 按内容指纹去重（命中则只更新使用次数）
   │    · 落库 + 按条数/天数淘汰
   ▼
SQLite
   │
   │ ④ item_captured 信号（跨线程）
   ▼
GUI 线程：刷新列表 + 状态提示
```

③ 之所以留在后台线程：识别、正则扫描、SQLite 写入都不涉及 Qt 对象，
放主线程会在连续复制时造成可感知的卡顿。

**截断必须排在隐私判定之后。** 判定读的是完整内容；先截断再判定，
「长文本里藏着密钥、且恰好落在截断线之后」这种情况会因为判定时
看不到那段内容而被放行 —— 顺序反了就是漏检。有专门用例守着这条。

截断只作用于文本类载荷（图片走 `image_path`、文件走 `files`，
没有 `content` 长度问题），原文长度写进 `metadata.original_length`，
否则用户看到一段被截断的内容，无从判断是不是被程序改过。

**淘汰的 `pin_immune` 开关**：为真（默认）时固定项完全不占
`history.max_items` / `max_days` 的额度，这是老行为。关闭后固定项也计入上限，
但排序仍把固定项排前（SQLite 的 `ORDER BY pinned DESC, …`，
JSON 后端的 `_sort_key`），所以先被淘汰的仍是久未使用的普通记录。
两个后端方法签名与语义逐条对齐。

**剪贴板形式为什么必须在「采集那一刻」收下来。**
`QMimeData` 是系统剪贴板当时那一份的快照，下一次复制就没了。
之后无论读多少次 `storage`，都只能拿到我们当初决定存下来的东西 ——
所以「这条记录还有没有 HTML 可用」是个**只能当场回答**的问题，
不能事后推导。判定与取用收在 `core/clipboard_formats.py`，
采集侧（`ui/clipboard_qt.py`）只负责把系统给的东西端过来。

**`metadata` 是共享信封，写入按键合并。**
往里写东西的至少有四个来源：采集（`last_source`）、形式（`formats`、
`text_bytes`、`formats_summary`）、同步（`pinned_by`、`synced`）、
截图识别（`ocr`）。`update_fields(metadata=...)` 因此是**合并补丁**语义：

- 传部分键 → 只改这几个，其余原样保留
- 传 `None` → 删掉这个键
- 传 `{}` → 什么都不改

此前是整体替换，于是每多一个写方，其它写方的键就开始轮流消失 ——
而且是静默的，没有报错、界面照常，只有某天发现某个字段莫名其妙没了。
「整体替换」还逼出一个反直觉的写法：想删一个键就得传整份拷出来的字典，
一旦哪个写方忘了拷，删除动作就变成一次全量覆盖。

### 检索

```
用户输入「上周的截图」
   │
   ├─ parse_intent()  拆成 {类型: 图片, 时间: 上周, 关键词: ''}
   │  └─ 歧义名词（「脚本」「文件」「图片」…）要**被结构组织过**才算类型过滤，
   │     见下方「类型名与日常名词」
   │
   ├─ 无关键词 + 有过滤条件 → storage.list(kind, since, ...)
   │  有本分支的原因：图片/文件类记录没有可检索文本，
   │  退回全文检索必然查空
   │
   ├─ _candidates()  取候选集：先问后端（SQLite 有 FTS5），再全库补齐
   │  └─ search_index.scan_items()  流式扫 iter_all()，带命中位置
   │
   ├─ _filter()  内存过滤（来源别名、多类型并集、时间上界）
   │
   └─ rank() 四信号加权排序
        相关度 + 时间衰减(半衰期 7 天) + log(使用频次) + 固定/收藏加成
```

排序权重集中在 `RankingWeights`，便于按用户习惯调整。

**类型名与日常名词。** `KIND_KEYWORDS` 里的词同时是常用名词，
而用户搜的常常正是他自己刚复制过的那几个字。所以 `parse_intent()`
先判断这个词**有没有被结构组织过**：

```
脚本               → 关键词「脚本」         （裸名词）
看下脚本            → 关键词「脚本」         （无结构，且有内容提示词）
收藏的代码          → 类型=代码 + 只看收藏   （「的」是定中结构信号）
所有文件            → 类型=文件             （量化限定词）
最近图片            → 类型=图片 + 时间=最近   （时间词前缀）
```

判据的默认方向是**不判为类型**。理由是不对称的代价：多召回几条只是让人扫一眼，
而把用户刚复制的那段文字从结果里筛掉，表现是「没有匹配的记录」——
用户只会以为工具坏了，甚至怀疑自己记错了关键词。

实现上有三个容易写错的地方，都写在 `AMBIGUOUS_KIND_WORDS` 与
`_is_type_query()` 的注释里：时间词会被提前摘掉（所以要显式传
`time_words_seen`）、类型词要按位置逐个替换（否则「所有链接 所有代码」
只解析出第一个）、长词要优先匹配（否则「截图」会被拆成「截」+「图」）。

**候选集是全库，不是最新一批。** 这是 `core/search_index.py` 存在的全部理由。

后端检索（`storage.search` / `repository.search`）会把 `LIMIT` 截在**结果集**上，
于是「最近这一批记录里有没有」决定了用户还能看到什么。实测过一个会误导人的场景：
真目标是正文命中但很老，另有 400 条只命中标签的新记录 ——

```
后端只返回标签命中的那 400 条（正文命中的那条被 LIMIT 切掉了）
语义层再按相关度排序，也只能在这 400 条噪音里排
用户看到 20 条噪音，真正要找的那条不在其中 —— 而库里它就在那
```

更糟的是两个后端不一致：JSON 那边是纯子串扫描、排序规则不同，
同一条记录换个存储方式就搜得到、又或者反过来。**结果不该取决于数据存在哪**，
所以 `tests/test_search_index.py` 里给同一份数据、同一句查询，
两个后端各跑一遍并断言结果相同。

分工是：后端检索命中够多时走快路径（省掉一次全库扫描），
不够时用全库扫描补齐，两边合并去重。`--search --json` 里的
`backend` / `scanned` 就是这个决策的现场记录 —— 结果集本身看不出
「为什么搜不到」，这两个数才是回答那个问题的。

`core/search_index.py` 另外承担两件事：

- **把「扫了多少条」变成可观测的。** `SearchOutcome.scanned` 让
  「没有匹配」与「没进候选集」在输出里长得不一样，用户不必怀疑自己记错了关键词。
- **跨查询复用一份全库快照**（`SearchIndex`）。搜索框按输入逐字触发，
  没有它每次都要重新遍历全库。失效策略是**整份丢掉重取**，
  而不是增量维护：增量要在采集、删除、合并、同步导入、切换存储五条写入
  路径上各挂一次钩子，漏一条就变成「新记录搜不到」—— 那正是它要消灭的症状。

`Application` 在这几条路径上都会 `_invalidate_search_index()`，
`tests/test_application.py` 逐条验「失效真的发生了」。

**为什么不上倒排索引。** 剪贴板里最常见的查询是短词（「记录」、`abc`），
这类词命中成千上万条，索引带不来召回上的收益，代价却是要在每次采集、
每次合并、每次同步导入时维护它 —— 而这些写入路径已经有各自的复杂度了。
实测 2 万条记录（平均 90 字符）一次全库扫描 30~95ms，够用到需要换掉它的那天；
那天的信号也很明确：`--search --json` 里的 `scanned` 会一直贴近库大小，
而用户开始抱怨搜索卡顿。上后缀自动机之类的结构要连带解决
「每次写入的维护成本」，那是另一个量级的改动，不值得提前做。

扫描本身在**小写化之后的字段**上做，这一点是量出来的而非推出来的：
同样 2 万条、命中密集的查询，预先把字段 `lower()` 出来是 49ms，
而「边找边判、只在失败时才 `lower()`」要 77ms。后者看起来省了一次拷贝，
实际让每次未命中都多试一遍 —— 而命中密集恰恰是最常见的情况。
两种写法都写过，结论留在代码注释里，免得后来人再走一遍。

## 平台适配

`ClipboardBackend` 定义了能力接口，每个方法都有「不支持」的默认实现。
子类只覆盖自己能做到的：

| 方法 | 用途 | 缺失时的表现 |
| --- | --- | --- |
| `read_primary_text()` | X11/Wayland 主选择区 | 返回空串，该功能不出现（开关也会被禁用） |
| `read_windows()` | 系统剪贴板历史 | 返回空列表，导入入口提示不支持 |
| `current_focus()` | 来源应用识别 | 来源显示「未知来源」 |
| `set_transient_text()` | 安全粘贴（限时清除） | 返回 False，改由定时器清空 |
| `history_exclusion_formats()` | 写入级「不进系统剪贴板历史」的格式名 | 返回空列表，仅依赖限时清空 |

`capabilities()` 返回能力矩阵，供设置页展示与功能降级。

**能力矩阵不是摆设。** 它必须真的参与功能开关：`primary_selection` 为假时，
设置页里「同时记录主选择区」应被禁用并写明缺什么；`transient_clipboard`
为真时，写入侧就真的要有对应实现。曾经这两处都写死过 `True` ——
声明了能力、实现是空的，看任何一处都显示正常。

主选择区的采集在 `ClipboardMonitor` 里走**独立通道**：独立的开关
（`monitor_primary`）、独立的指纹、独立的节流（`primary_interval_ms`）。
不共用剪贴板那套的理由是行为差异：剪贴板「变了就是复制了」，
而主选择区跟着拖选走，读取本身就得充当防抖。

**出站防护**（`core/copy_guard.py`）收在一处：`plan_outbound()` 决定
「这条内容复制出去要不要挂排除标记、要不要限时清空」，`ClipboardReleaser`
负责到期后的**带条件**清理（只在内容仍是我们写的那份时才清）。
平台差异由 `history_exclusion_formats()` 表达，Qt 写回时把格式名挂到
剪贴板数据上 —— 必须在写入时声明，内容进了系统历史就取不回来。

**Windows** 用 `ctypes` 直接调 Win32，零第三方依赖：

- `GetClipboardSequenceNumber` 做低成本变化检测
- `AddClipboardFormatListener` 事件驱动，避免轮询空转
- `OpenClipboard` 带重试，因为其它进程常短暂占用剪贴板
- 写入时附加 `ExcludeClipboardContentFromMonitorProcessing`

系统剪贴板历史（Windows 10 1809+）走 WinRT
`Clipboard.GetHistoryItemsAsync()` 读取，补齐本工具启动前的记录。
两个必须注意的点：

- **开关要读注册表**：`HKCU\Software\Microsoft\Clipboard\EnableClipboardHistory`。
  单看 API 能否调用是分不清「没开历史」和「历史是空的」的。
- **导入走 `Collector.process()`**：与实时采集同一条管线。
  若为了「快一点」直接写 storage，系统历史就成了绕过隐私判定的后门。

**Linux** 区分 X11 与 Wayland：

- Wayland 走 `wl-paste` / `wl-copy`，全局快捷键交给桌面环境
- X11 优先用 Xlib 读 PRIMARY 与 `_NET_ACTIVE_WINDOW`，无 Xlib 时退到命令行工具
- `XGrabKey` 注册时同时抓 NumLock/CapsLock 组合，
  否则用户开着这些锁键时快捷键会失效

**macOS** 只用系统自带命令，不强制依赖 pyobjc：

- `pbpaste` / `pbcopy` 读写剪贴板（`-Prefer txt` 拿纯文本）
- `osascript` + System Events 取前台应用与窗口标题
- 临时剪贴板：`pbcopy` 到期后写空内容，**但只在内容仍是当初写入的那份时才清**
  （否则用户在这期间复制的东西会被误删）。进程退出后定时器即失效，
  所以这只是「缩小暴露窗口」，不是擦除痕迹 —— 处理密钥请走
  「不落盘 + 复制出站打码」那条路

### 能力自检

平台代码有个特殊的验证难题：**接口对得上，功能可以是空的**。
macOS 的全局快捷键曾只探测 pyobjc 能否导入，`register()` 从未覆写，
继承基类的假实现永远返回 `False`；Windows 的事件通道装了 Qt 过滤器，
却没注册 `AddClipboardFormatListener`，`WM_HOTKEY` 也没有分发函数 ——
「注册成功、回调永不触发」，比注册失败更难发现。

两者在 Linux 上都看不出问题（`backend_name` 显示正确、`is_available` 为真、
`register()` 返回真）。所以需要一条**在真机上按真实调用链验一遍**的路径：

```
utils/selfcheck.py     # 产品内实现，装进 --selfcheck
tools/native_check.py  # 真机手工跑一次的扩展脚本（含平台专有项）
```

三级判定不能压成一句「不支持」，因为最常用的中间态恰恰是「降级但可用」：

| 判定 | 含义 | 需要动作 |
| --- | --- | --- |
| `ok` | 调通了 | 无 |
| `degraded` | 调不通但已按设计降级 | 通常无 |
| `fail` | 预期应能用却没有 | 需排查 |

自检**只读**：不改写剪贴板，唯一副作用是注册并立即撤销一个
`Ctrl+Alt+Shift+F24`（刻意选一个不会被占用的组合）。
它刻意不打开数据库 —— 自检回答的是「这台机器上原生能力能不能用」，
不该被历史文件损坏之类的问题挡住，否则最需要它时恰好用不了。

后端实现 `sanity_check()` 提供只读探测，返回
`(是否可用, 人类可读的原因)`。这是**新增原生能力的硬性要求**：
没有它，自检只能验「接口在不在」，验不出「功能空不空」。

## 存储

历史有两种落盘方式，接口相同、可互换，由 `storage.backend` 决定：

| | `core/storage.py` | `core/repository.py` |
| --- | --- | --- |
| 介质 | SQLite 单文件 | 单个 JSON 文本文件 |
| 检索 | FTS5（`trigram` / `unicode61`），候选不够时由 `search_index` 全库补齐 | 进程内扫描 + 字段权重打分 |
| 图片 | `images/` 下的独立 PNG | 默认内联为 data URI |
| 默认 | ✅ | 需显式切换 |

两者暴露同一组方法（`add`/`get`/`list`/`search`/`find_by_hash`/`touch`/
`update_fields`/`delete`/`clear`/`enforce_limits`/`stats`/`close`），
所以 `Application`、CLI、同步模块都不必判分支 —— `open_repository()` 是唯一入口。
这不是过度抽象：同步模块写日志时也要读「本地有哪些 hash」，
两套后端各写一遍迟早会不一致。

### SQLite 后端

单表 `items` + FTS5 虚拟表，靠触发器保持同步。

```sql
items(id, kind, content, preview, html, rtf, image_path, image_width,
      image_height, files, metadata, source_app, source_title, hash,
      size, pinned, favorite, sensitive, tags, device,
      created_at, used_at, use_count)

items_fts(content, preview, source_app, tags)   -- external content 表
```

几个细节：

- **`trigram` 分词器**：中文和代码片段没有空格，`unicode61` 会整段当一个词。
  `trigram` 按 3 字符切分，对这类内容友好。不可用时退回 `unicode61`。
- **FTS 查询串要转义**：用户输入里的 `AND`、`"`、`*`、`:` 都是 FTS5 语法字符，
  未转义会抛语法错误。实现里按 token 拆分并加引号。
- **短查询走 LIKE**：`trigram` 查不到 3 字符以下的词，
  「剪贴」这种两字中文必须由 LIKE 兜底，所以 FTS 未命中时会再试一次。
- **图片落盘策略**：PNG 存 `images/`，数据库只存相对路径；
  按内容哈希命名，同一张图重复复制只落一份文件。

### JSON 后端

格式刻意做成一眼能读、能手改：空字段不落盘，中文不转义，
每条记录带 `hash` 便于去重与跨设备对账。

几个必须处理的点：

- **原子写**：先写 `.tmp` 再 `os.replace`。直接 `write_text` 在进程被杀时
  会留下半截 JSON，整份历史就废了。
- **损坏不致命**：解析失败时把原文件改名成 `.json.broken` 再重建，
  用户还能自己抢救，而不是启动即崩。
- **图片内联**：`set_image_data()` 登记「相对路径 -> data URI」，
  落盘时写进记录的 `image` 字段。读取端按
  「参数是 data URI -> 登记表 -> 记录内联 -> 同名文件」依次定位，
  最后一级是为了兼容从别处导入、图片未内联的 JSON。
- **写入是整文件重写**：这是刻意的取舍。剪贴板是秒级低频操作，
  几千条记录重写只有几毫秒；换成追加式日志就得处理 `compact` 与半行损坏，
  复杂度不值得。记录量到十万级时应改用 SQLite，而不是优化这里。
- **并发**：单把 `RLock` 保住「读-改-写」，因为每次写都基于内存态整体重写，
  分片锁换不来收益。

### 关闭之后的行为（两个后端一致）

`close()` 之后仍有调用方找上来是**常态**，不是异常：界面的搜索防抖定时器、
采集线程、限时清空任务都可能晚一步到达。这些调用跑在 Qt 事件循环里，
抛出的异常会被 Qt 吞成一行 `Exceptions caught in Qt event loop`，
表现是「关窗时刷一屏 traceback」或「设置页莫名不刷新」，很难追回源头。

所以两个后端的约定是：

| 调用 | 关闭后的行为 |
| --- | --- |
| 查询（`list`/`search`/`get`/`count`/`stats`…） | 返回空结果，形状与空库一致 |
| 写入（`add`/`touch`/`update_fields`/`delete`…） | 静默忽略 |
| `close()` | 幂等，重复调用直接返回 |
| `closed` | 只读属性，界面据此跳过刷新 |

排查这类问题靠 `closed` 这个属性：它把「存储还能不能用」变成一次普通判断，
而不是等异常从事件循环里冒出来。

窗口侧配套两件事（`main_window.py`）：

- `shutdown()` 停掉搜索防抖定时器，并断开对外信号 —— 定时器到期时窗口
  可能已经回收，而那时存储多半也关了
- `reload()` 先看 `storage.closed`，关了就只清空列表，不发起查询

`Application.quit()` 在 `storage.close()` **之前**调 `window.shutdown()`，
顺序不能反。

### 内容归一（判重的前置步骤）

「相同内容只保留一条」需要一个判据，而这个判据不能是原始字节。
同一个页面被不同渠道分享出的链接、同一个文件的不同写法，字节不同但语义相同：

```
https://shop.example.com/item/42?utm_source=weibo&spm=a1z.123
https://shop.example.com/item/42?utm_source=wechat&ref=abc
https://shop.example.com/item/42
```

按字节比是三条，按用户的理解是一条。`core/normalize.py` 在算指纹之前
先做一次归一：

- `normalize_url()` — 去跟踪参数（`utm_*` / `spm` / `fbclid` / `ref` 等）、
  查询参数排序、主机名小写、去末尾斜杠、折叠重复 `/`
- `normalize_path()` — 折叠重复分隔符、消解 `.` 与 `..`、去末尾斜杠
- `canonical_content(kind, text)` — 按类型分发，其余类型原样返回

**归一只用于算指纹，不写回 `item.content`。** 用户看到的、粘贴的、搜索的
仍是原文；改写内容等于篡改用户数据。数据流上的位置：

```
剪贴板 → classify 识别类型 → normalize 归一 → content_hash 算指纹 → 落库
                              ↑
                    只用归一结果算 hash，content 保持原样
```

**判据必须保守。** 误合并比不合并更糟：不合并只是列表多几行，
误合并会让用户找不到东西，且原始内容已被删除、无法恢复。所以只剥掉
明确无意义的装饰，拿不准的一律保留：

| 保留 | 原因 |
| --- | --- |
| `?v=` / `?id=` / `?page=` 等参数 | 可能真的决定页面内容 |
| `#` 片段 | 单页应用靠它区分页面 |
| 无 scheme 的写法 | `example.com/x` 与 `https://example.com/x` 可能真是两个东西 |
| 短链 | 展开要发网络请求，且结果不可控 |

`history.canonical_dedupe` 及其子项 `url` / `path` 可分别关闭。
关掉后行为与改造前完全一致（按原始字节判重）。

**存量数据需要重算。** 归一是后加的规则，此前入库的记录指纹是按原始内容
算的，不重算就永远合不了。两个后端都提供 `recanonicalize(options)`：
只改 `hash` 字段，`content` 不动。CLI 的 `--merge-duplicates` 会先调它
再调 `dedupe()`，顺序不能反 —— 反过来 `dedupe()` 按 hash 分组根本
看不出老记录之间重复。

同一份跟踪参数定义还被 `automation.py` 的 `url.strip_tracking` 转换器复用：
两处各维护一份名单迟早分叉，用户会看到「转换说没有跟踪参数、去重却认为
这是两条不同的链接」这种自相矛盾的结果。

### 重复内容合并

`history.merge_duplicates`（默认开）决定「同一段内容被复制多次」怎么记：

- **开**：采集时命中 `find_by_hash`，不新增行，改为 `touch()` 累加 `use_count`
- **关**：每次复制各自成行，重复项留在列表里

两种情况下都会出现「同一 hash 存在多行」的历史数据（关闭期间产生、
或从别处导入）。`dedupe()` 负责把它们收拾干净，关键在于**它是一次合并，
不是一次删除**：

```python
# 删行之前，先把重复行的频次折算到保留项
total = SUM(use_count) + (行数 - 1)
used_at = MAX(used_at, created_at)   # 组内最新时间戳
```

三个容易写错的地方：

- **`+ (行数 - 1)` 不能省**。重复行本身就是「又复制了一次」的凭据，
  只是没记在 `use_count` 上。只累加 `use_count` 会得到 0，
  等于把「复制过 3 次」合并成「从没复制过」——高频片段反而排在低频片段之后。
- **`used_at` 要提到组内最新**。保留行是按 `MIN(id)` 选的，
  它的 `used_at` 可能是组里最旧的时刻；不提升就会在「按最近使用排序」里沉底。
- **必须幂等**。合并后再跑一次应当返回 0 且不再改动数据，
  否则定时任务反复调用会持续放大 `use_count`。

两个后端的实现形状不同（SQL 聚合 vs 内存分组），但语义必须逐条对齐 ——
`tests/test_storage.py` 与 `tests/test_repository.py` 里各有一组同名用例守着。

#### 频次只有一个口径

`use_count` 是复制频次的**唯一**来源：排序权重读它，界面显示它，
合并时折算到它。早期实现另写过一份 `metadata["copies"]`，结果它没人读、
还和 `use_count` 差一位（新增记 0、复用记 1），成了两个互相打脸的口径 —— 已移除。
需要扩展元数据时（例如 `last_source`）往 `metadata` 写没问题，
但任何「计数」都必须落在 `use_count` 上。

## 配置生命周期

配置看起来是最不需要设计的一层，但这个项目在它上面栽过同一个跟头 7 次：
**配置项声明了、设置页显示了、代码里没有读取方。**

```
DEFAULTS["ui"]["card_density"]  ←  声明
settings_dialog 里的控件         ←  显示（后来才补上）
（源码里任何地方）               ←  没有读取方
```

后果不是报错，是「勾了没反应」：用户以为是自己的用法不对，
排查起来只能靠读源码。

### 三层保障

| 层次 | 做法 | 拦住什么 |
| --- | --- | --- |
| 定义 | `SCHEMA_VERSION` 是版本号的唯一来源，`DEFAULTS` 从它取值 | 两处各写一个数字然后分叉 |
| 迁移 | `_migrate()` 按版本逐档转换，只在格式不兼容时加一档 | 旧配置文件在新版程序里语义错位 |
| 审计 | `--config-audit` 拿每个键去源码里找读取方 | 「加了配置项忘了接上」 |

### 审计的判据

刻意保守，只报**连一次字符串引用都没有**的键：

- `config.get("a.b")` / `_config.get("a.b")` 任一形式都算读到
- 子键可能被拼出来（`config.get("ocr." + name)`），此时**上一级**父键的
  字面量出现即算这一支活着；再往上放宽会把「段里有的键读了、有的没读」
  这种最常见的空转形态一起漏掉，所以到父级就停
- `ui/settings_dialog.py` **不算读取方** —— 它只是把界面上的值写回配置，
  写回去不等于会生效
- `meta.*` 由配置模块自己消费（迁移流程），单独放行

### 迁移的两个约束

- **只升不降**：文件版本比程序新（用户装回旧版）时原样保留，不改也不报错。
  降级转换无从写起，硬改只会丢数据。
- **失败保留原文**：迁移函数抛异常时退回原配置 + 默认值，并记日志。
  一个转换函数的 bug 不该让用户打不开程序。

展开平铺键 → 迁移版本 → 与默认值合并，顺序不能变：
反过来迁移函数看到的就是错形状的配置。

## 隐私

`PrivacyGuard` 是所有判定的唯一入口 —— 采集、同步、复制出站都调它，
避免「主流程过滤了、同步漏了」这类不一致。

判定分两级：

1. **拒绝记录**：PEM 私钥；来源命中密码管理器黑名单。
2. **标记敏感**：API Key、JWT、身份证、银行卡、密码字段等。
   标记后**默认不落盘**（`sensitive_retention_seconds = 0`），
   用户可在设置里改成限时保留，由定时任务按 TTL 清除。

脱敏规则支持用户自定义正则，非法正则在加载时跳过并告警，不影响其它规则。

「跳过并告警」这半句是这里唯一的风险点：告警写在日志里，用户不会去看，
于是「我加了一条保护」和「这条保护静默失效」在界面上完全一样。
所以 `core/privacy_audit.py` 提供了一条能把这件事问清楚的路径：

| 命令 | 回答的问题 |
| --- | --- |
| `--privacy-audit` | 实际装上的规则有哪些、哪条编译不过、哪条试跑不命中 |
| `--redact TEXT` | 拿一段真实内容试跑，看会被替换成什么 |

两个约束决定了它怎么写：

- **体检对象是 `PrivacyGuard` 装上的规则，不是配置文件里的文本**。
  编译失败的规则不会出现在 Guard 的规则表里，只从 Guard 取就会漏报
  最该报的那一条。所以报告把「配置里声明的」与「Guard 装上的」取并集。
- **没有样本 ≠ 规则有问题**。自定义正则千变万化，拼不出样本时报告只写
  「没有可用于验证的样本」，`will_run` 仍为真 —— 否则 `healthy` 会与
  界面上的 ✗ 自相矛盾，用户白跑一趟。样本能拼出来时再自查一遍：
  「拼出的样本必须命中自己的正则」，拼不对就当没有样本。

样本由 `_literal_sample()` 从正则本身拼出（`EMP\d{6}` → `EMP111111`），
只处理字面量、字符类、转义类与紧跟的量词；遇到否定字符类、前瞻等
无法安全构造的结构就返回空串。**宁可说「验不了」，也不给一个必然失败的样本**。


## 同步

不设中心服务器，两种模式共用一套「每设备一个日志文件」格式。

```
shared-folder/
├── laptop.llsync     ← 每台设备只追加自己的
├── desktop.llsync
└── server.llsync
```

好处是**天然无写冲突**：多台机器同时同步也不会损坏文件。
文件内部按「4 字节大端长度 + 载荷」分块，读取时逐块解析，
单块损坏只丢那一条，不会让整个日志不可用。

加密用 Fernet（`cryptography`），密钥由口令 + 固定盐经 PBKDF2 派生。
未安装 `cryptography` 时自动退化为明文并在日志告警一次 ——
可选依赖缺失不应该让整个功能不可用。

导出侧的过滤规则与采集侧一致：敏感内容、图片默认都不出本机。

### 用户标记（固定 / 收藏）为什么取并集

`SyncRecord` 除了内容与 `tags`，还带 `pinned` / `favorite` 两个布尔标记。
加上它们之前，这里有个**静默丢数据**的缺陷：内容同步得好好的，
用户显式做的标记却跨不过去，而且两处各挡一次 ——

```
导出侧：按「内容已发过」跳过 → 标记的后续变化没有发出机会
导入侧：按「指纹已存在」跳过 → 就算发出去了也不会被读
```

两道门都在「内容层面」判断，于是标记这个**与内容无关的状态变化**
在两条路上同时被过滤掉。用户只会在另一台机器上发现
「我明明收藏过，怎么没了」。

改法分两处，缺一不可：

- **导出侧补发**。内容已发过时，再比一次「本地标记 vs 日志里已发出的
  标记」（`_local_flag_state()` 取并集）。本地更多才追加一条，
  避免每轮重传全部历史把日志撑爆。
- **导入侧合并**。`apply_flags()` 是模块级函数，两种同步模式共用 ——
  两条路径各写一套规则的话迟早分叉（墓碑处理当年就踩过这个坑）。
  命中已存在的记录时不再直接 `continue`，而是把标记并进去。

**合并方向默认是并集，不是最后写入者胜。**

| 动作 | 结果 |
| --- | --- |
| A 固定，B 也固定 | 一真即真 |
| A 固定，B 先删了再同步 | 保留 |

并集的理由是它不会**悄悄弄丢**用户的显式标记 —— 丢一个「我特意标过」
的标记，比多留一个可再取消的标记贵得多。

但并集单独用有一个明确的代价：**取消传不出去**。同步通道里「那边取消过」
和「那边从没设过」的表示完全相同（都是本地 False），没有额外信息就无法区分。

### 取消的传播：与墓碑同性质的「事件」通道

于是有了 `core/flag_changes.py` —— 把「取消」本身变成一个
**带时间戳的事件** 记录下来，随同步传出去。这样「我在笔记本上取消了」
才是一个能被传播的事实，而不是靠猜。

判定规则是 **设备内取最新、设备间取并集**：

| 动作 | 结果 |
| --- | --- |
| 本机设过又取消 | 取消生效 |
| 本机取消，另一台设过 | 标记**保留**（那是那台的显式意图） |
| 同一台反复切换 | 时间戳最大的那次生效 |

时间戳只用于在**同一台设备内**排序，跨设备不比较先后 —— 所以
**不要求设备之间时钟同步**。跨设备一律并集，而并集不依赖时间。

几条必须说清的实现约定：

- **变更不受增量游标约束**。它的时间戳是「用户做那个动作的时刻」，
  与同批内容记录的 `created_at` 不同源。按游标裁掉的话，一条晚到的取消
  （对端离线一阵才上线）会永远传不过来 —— 而取消恰恰是「对端曾经收过
  这个标记」的后续事件，漏一次就没有第二次机会。
  同理，变更记录也**不参与游标推进**，否则游标会跳到一个与内容无关的时刻。
- **先落变更、再处理内容**。与墓碑「先删后写」是同一类批内顺序问题：
  顺序反了，取消会被同批内容的并集盖回去。
- **只靠内容记录碰不到它**。内容只发一次，标记变化是之后的动作，
  所以变更到达时同批里往往没有那条的内容记录 —— 只靠内容循环里的
  `apply_flags()` 永远碰不到。为此额外有 `_apply_flag_change()`：
  按指纹找本地记录、用解算出的终值落地。
- **取消后清掉来源设备**。否则一个过期的 `pinned_by` 会跟着
  「未固定」的记录漂到后续同步里，删除保护的判断会读到过期的设备名。
- **导入侧无标记时也要看变更存储**。取消恰恰是以「记录上什么都没有」
  的形式表达的，直接 `return False` 会把取消吞掉。
- **幂等**：同一个值重复登记不新增 —— 否则界面刷新会不断往文件里追加事件。
- **不传 `flag_changes` 时退化为纯并集**，行为与改造前完全一致，
  既有调用点（含第三方）不受影响。

并集与取消的取舍关系一句话概括：**并集管「有没有人设过」，
事件通道管「最后一台设过的设备后来说了什么」**。两者缺一不可。

### 局域网：写出响应即视为送达

局域网是**拉取模型**，服务端只有在把响应写出去之后才知道对端拿到了数据。
墓碑与标记变更都不受 `since` 约束（每次同步都会带上），所以必须有
「已送达」的确认，否则每轮都在重传全部历史事件。

确认的位置就在 `_send_json()` 成功之后：`wfile.write` 失败会抛异常，
走不到确认那一步，事件保持待发、下轮重传 —— 宁可重复告知，也不能漏。

> 这里此前是个真的洞：代码里从来没有对局域网做 `ack()`，
> 于是文档写的「送达过的不再复述」在局域网模式下从未生效。

### 增量游标

`core/sync_cursor.py` 记录每个同步来源「已经拉到哪里」，让同步只处理新记录。

早期实现每轮都从 `since=0` 开始，靠内容指纹去重保证不重复。这在记录少时没问题，
但剪贴板历史会涨到上万条，于是「只新增了一条」的同步仍要重扫全部历史，
收益全被无效功吃掉。游标解决的就是这一点。

```
数据目录/
└── sync_cursors.json      ← {"cursors": {"lan:192.168.1.9:48620": [1790497962.2, 1005], ...}}
```

每项是 `[时间戳, id]`。旧版写的裸时间戳仍可读（按 `id = 0`），不需迁移。

关键约定：

- **键 = 同步模式 + 来源标识**。共享文件夹用 `folder:<对端日志文件名>`，
  局域网用 `lan:<host>:<port>`。多对端各自推进，互不干扰。
- **游标是 `(created_at, id)` 复合值，不是单纯的时间戳**。这一点是本文件里
  最容易看轻、后果也最重的一条，单独在下一节展开。引入 `id` **不是**
  退回「自增序号游标」：`id` 只在 `created_at` 相同时作次级键，
  跨时刻的判断仍以时间戳为准，所以对端 `compact()` 清理日志不会让它错位。
- **只在成功导入后推进**，且取「本批记录的最大 `(created_at, id)`」。
  对端不可达、口令错误、解密失败时保留旧游标 —— 否则对端短暂离线，
  那段时间的记录就被永久跳过了。
- **只增不减**（`advance()` 取 `max`，按 `(created_at, id)` 字典序比较）。
  多对端同步时若某对端返回旧位置，不能把已同步的进度反向拉低；
  同一时刻内 `id` 更大的才是更靠后的位置，只比时间戳会把这层信息丢掉。
- **留 1 秒安全窗口**。同一时刻写入的多条记录共享时间戳，游标会回退该窗口再请求。
  边界记录可能重复拉取，但指纹去重是幂等的，用少量重复换取不漏。
  回退时 **`id` 部分归零**：回退意味着该时刻的记录要整批重读，
  只回退时间却仍按 `id > 游标` 过滤，会漏掉回退区间里 id 较小的记录 ——
  回退本是为了多读，不能反而读漏。
- **损坏即重置**。JSON 解析失败时丢弃游标从 0 重来，只是慢一轮；
  游标文件本就是可牺牲的缓存，不该让同步因此失败。

### 同刻记录塞满一页：游标必须靠 `id` 继续前进

这是比「翻页」更隐蔽的一类缺陷，因为它在**修好翻页之后**仍然存在。

剪贴板里「同一时刻挤进大量记录」并不罕见 —— 紧密循环写库、
批量导入系统剪贴板历史（`core/native_history.py`），都会让同一毫秒落进大量记录。
此时只记时间戳的游标会彻底卡死：

```
首页返回满页（500 条），created_at 全是 T
下一页请求 created_at > T ── 得到 0 条
剩下的记录不是「更旧」，是「一样新」── 既不在这一页，也永远不在下一页
```

安全窗口救不了这个：回退一秒只是把同一页从头重读，再退到同一个位置，
永远推进不了。实测 1005 条同刻记录，旧实现只同步到前 500 条，
**剩下 505 条永久缺失**，且每一轮都是这个结果 —— 没有任何报错。

解法是让游标能表达「同一时刻内读到哪一条」：

- **本地遍历**：`Storage.iter_since` / `JsonRepository.iter_since` 都接受
  `since_id`，边界语义统一为「`(created_at, id)` 字典序严格大于」。
  `since_id == 0` 时退化为只比时间（`created_at > since`），
  保持与旧行为兼容。两个后端必须逐条同语义 —— 同步模块不区分后端，
  分叉的后果是「换个存储后端就少一段历史」，且同样没有报错。
- **局域网**：响应里给每条内容记录带上 `seq`（发送方的 `id`），
  客户端取本页最大的 `(created_at, seq)` 作为下一页游标。
- **`seq` 不写进共享日志**。它是发送方的库内编号，接收方靠 `hash` 判重、
  靠 `created_at` 排序，用不上它；写进 `to_json()` 会改变共享格式，
  还要处理老版本读到未知字段。`from_json()` 读它只是为了兼容局域网载荷，
  缺失时落回 0。
- **对端是旧版本时明确告警**。响应里没有 `seq` 又恰好「同刻记录塞满一页」，
  本侧会在日志里警告并结束本轮（不死循环、不静默跳过），
  剩余记录等对端升级后补齐。旧版本没有能表达「同刻内读到哪一条」的字段，
  这一点无法在本侧绕过。

`since` 参数仍可显式传入（覆盖游标），`--export-sync` / `--import-sync` 场景用得上。

### 翻页与「全量可见」

游标解决「别重复拉」，另一半是「**一条都别漏**」。传输是分页的
（共享文件夹 `limit` 默认 500，局域网 `DEFAULT_PAGE_SIZE` 500），
而「一页」和「全部」是两个概念 —— 混用会产生静默丢数据。

原先两条路径都只碰了一页，且候选集来自 `Storage.list(limit=N)`：

```
`list()` = 界面排序下的前 N 条（含 used_at，会随复制变化）
```

于是记录超过 N 条时，第 N+1 条起永远进不了传输范围。对端游标被推到
第一页的最大时间戳，更老的记录都比它早，**再也不会被请求**。
没有报错，`--sync-status` 也照常显示进度 —— 它以为 500 条就是全部。

关键在于这个错误会**自我固化**：那 500 条被 `_local_hashes()` 记为「已发送」，
下一轮仍是「取最新 500 条 → 全部已发送 → 导出 0 条」。加多少轮都不会补上。

约定：

- **遍历必须覆盖整库**，且顺序**稳定**。共享文件夹的导出用
  `Storage.iter_all()`（`id DESC` 键集分页）：`id` 严格递增、不随用户操作变动。
  不能用界面排序 —— 它含 `used_at`，用户复制一下记录就换位，
  翻页会漏读或重复读。
- **局域网按 `(created_at, id)` 升序**（`Storage.iter_since`）。对端用时间戳做
  游标，必须时间升序读才能「读完一批就推进游标」。`id` 作次级键给出全序，
  同一毫秒的多条记录不会因次序不稳而漏读。
- **客户端翻页直到某页不满**，持久化游标**只在整轮翻页结束后推进一次**。
  中途失败保留旧值，下轮从同一位置重来。
- **翻页要有保险丝**。理论上「某页不满」就会退出，但仍加了一个页数上限，
  免得服务端行为异常时进程空转。
- **去重集合同样要完整**。判「本地有没有这条」的 `seen_local` 以前也是
  `list(limit=MAX_SYNC_ENTRIES)`；本地历史超过该上限时，老记录不在集合里，
  对端每轮重放都会把它们再写一遍，历史里出现重复行。

新增任何「遍历历史」的代码时，先问一句：**这个顺序在记录被复制、固定之后
还稳定吗？它看得到全库吗？** 两个问题的答案都必须是「是」。

局域网直连是另一种模式（不依赖网盘），见下面「局域网同步」一节。

### 删除标记

`core/tombstones.py` 让「删除」也能跨设备传播。

同步原本只传「有什么」。用户在 A 上删掉一条记录，B 那边看不出发生过什么，
下一轮同步还会把它送回来 —— 删除在别的设备上等于没有。墓碑补上「没有什么」。

```
A: 复制 → 同步给 B（两边都有）→ A 上删除 → 记指纹 → 随日志传给 B → B 删掉那份
```

落盘是一行一个指纹，不含内容：

```json
{ "version": 1, "retention_seconds": 604800,
  "deleted": [{"hash": "c5cc4dd9…", "deleted_at": 1790497962.2}],
  "acked":  {"c5cc4dd9…": 1790497990.1} }
```

关键约定，每条都对应一个真实会发生的错误：

- **只记指纹，不记内容**。带上被删内容就成了「删除后仍留一份副本」，
  与删除的本意相反。指纹是单向的，够用来判「这条别要了」。
- **不是全集，是 7 天过期的缓存**。删一条记一条、到期即丢，长年使用只涨到常数级；
  「删除要传播」与「重装后想恢复历史」才不会互相拖累。
- **`acked` 与 `deleted` 分开记**。送达过的不再复述，否则每轮都要重传全部历史删除；
  但仍留在文件里，便于排查「这条为什么被删了」。
- **只有显式删除才记**。界面删除、`--remove`、`--clear` 记账；
  压缩淘汰与敏感过期是本机自己的整理，不扩散到别的设备。
- **对端离线超过保留期就不追删**。那时对端的副本已「活」了很久，
  删掉它等于丢对端自己的数据；只记指纹避免它被写回来。
- **固定项不被对端删除清掉**。用户显式标了「别动它」，删除传播不越过这条线。
- **批内删除优先**。游标有 1 秒安全窗口，同一批里可能同时出现「内容」与
  「该内容的删除」。读取时先应用全部墓碑、再导入内容，
  否则删除会被紧随其后的内容记录覆盖回去。
- **发送侧不能被「已导出」过滤掉**。导出本来就有「发过的内容不再重复发」的规则，
  墓碑若沿用同一条过滤会全被拦掉 —— 而「内容已发过」恰恰是删除要传达的前提。
- **写不进去只告警**。墓碑文件损坏或不可写时丢弃重来，删除本身照常生效。

两条同步路径共用同一套语义：共享文件夹走日志文件，局域网走只读 HTTP 接口，
两处的 `_apply_tombstone()` 判定逐条对齐（过期、固定项、幂等）。

## 图片附件（`images/`）

`core/image_store.py` 收口「图片文件谁来删」这件事。

背景是一类**看不见**的泄漏：记录被删掉之后，`images/` 里那份 PNG 没人来收。
三条路径都漏，且都不报错：

| 路径 | 原因 |
| --- | --- |
| `enforce_limits()` | 直接 `DELETE FROM items`，不像 `delete()` / `clear()` 那样顺手删图 |
| `purge_expired_sensitive()` | 同上。而这条路径里最要紧的恰恰是密钥/证件截图 —— 到期不删图等于没删 |
| 采集期被拦下 | 文件在 `_from_image()` 里已落盘，隐私判定在之后的 `Collector.process()` 里 |

外加一条只有 JSON 后端才有的：`delete()` / `clear()` 在 SQLite 上删图、
在 JSON 上不删 —— 「换个存储方式，磁盘表现就不一样」。

### 判据只有一个：有没有记录引用

回收靠的是「引用集」，不是「文件名像不像垃圾」：

```python
referenced = storage.referenced_images()      # 全库的 image_path 收敛成文件名集合
image_store.sweep(images_dir, referenced, dry_run=True)
```

按**文件名**比对而不是完整路径：库里历史遗留了 `images/x.png` 与 `x.png`
两种写法（还有绝对路径、data URI），不归一就会把还在用的图当成孤儿删掉。
归一的实现在 `image_store.normalize_relative()` / `basename_of()`。

### 删记录时不能无条件 `unlink`

图片按内容哈希命名（`_from_image()` 里的 `digest`），所以同一张截图被复制两次
只落一份文件。`merge_duplicates` 关掉时两条记录会共存并共用这个文件 ——
删其中一条就 `unlink`，另一条的图片会平白失联。

所以两个后端的 `_remove_image()` 都先问一句「还有别人引用吗」，
确认没有才删。`test_image_store.py` 里那条 `test_delete_keeps_image_still_shared`
就是钉这个的（两个后端各跑一遍）。

### 采集侧的回滚

图片是**先落盘、后判定**的：`QtClipboardAdapter._from_image()` 写下文件并返回
`ClipboardItem`，隐私判定、类型开关、去重都在之后的 `Collector.process()` 里。
任一不过，那份文件就没有主人。

`Collector._discard_image()` 负责收回去，走的是存储层的
`discard_unreferenced_image()` —— 判据仍交给存储层，因为采集侧拿不到完整引用集，
自己动手删会误伤「已被别的记录引用」的同一份文件。

### 只碰自己写下的东西

`iter_image_files()` 只产出目录下的**普通文件**且扩展名匹配 `*.png`。
子目录不递归、符号链接跳过、别的东西一律不动。`images/` 可能被用户指向
同步盘（或手工往里放了自己另存的截图），误删的代价远大于多留几 MB。

代价写在 README 的「已知限制」里：手工放进该目录、又不在任何记录里的文件，
会被 `--images-gc` 当成垃圾删掉。

### 「文件不在」与「垃圾没清」要分开

两者在目录列表里长得完全不同，但都不该混着报：

- `unreferenced` —— 目录里有、没记录提到。**待回收**。
- `missing` —— 记录提到了、文件不在。**数据损坏**（图片被手工删了、
  同步盘冲突丢了），要去找回来而不是清掉。

`ImageUsage` 两类都报，`--images` 与设置页各说一句。

## OCR

`core/ocr.py` 把「图片里的文字」变成可检索的 `content`，从而复用既有的
FTS5 索引与排序，检索路径零改动。

```
图片 ClipboardItem（kind=image, content=''）
   │
   │ Collector._enrich() 里最先执行
   ▼
OcrEngine.recognize_full()
   │  · 语言解析：ui.language → tesseract 语言串（chi_sim+eng）
   │  · 语言挑选：与「已安装语言」取交集，缺则回退（见下）
   │  · 缓存：按「路径 + 大小 + mtime」命中，同一张图不重复识别
   │  · 降级：后端不可用 / 超时 / 识别为空 → 返回空结果，不抛异常
   ▼
item.content = 识别文本；item.metadata['ocr'] = {置信度, 语言, 耗时}
                识别失败时 metadata['ocr'] 带 error / error_detail
```

### 两段式语言处理：想要的 vs 能用的

语言处理刻意分成两步，混在一起就没法单独观察「用户配了什么」：

| 函数 | 回答 | 是否查已装语言 |
| --- | --- | --- |
| `resolve_languages(locale, requested)` | 用户**想要**什么 | 否，纯字符串映射 |
| `select_languages(installed, locale, requested)` | **能用**什么 | 是，取交集后回退 |

为什么必须做第二步：**tesseract 只要有一个语言的数据文件不存在就整批失败**，
不是忽略那一个语言。`chi_sim+jpn` 在只装了 `chi_sim` 的机器上，
stdout 为空、退出码 1，**一个语言都用不上**。

```
想要 chi_sim+jpn，已装 chi_sim+eng
   交集 → ['chi_sim']              → 用 chi_sim，标记 partial
想要 jpn，已装 chi_sim+eng
   交集为空 → 回退 eng              → 用 eng，标记 fallback
想要 eng，已装 osd only
   osd 不算正文语言 → 无可用语言     → 不调用 tesseract，报 no_language_data
```

回退后 `LanguageChoice` 带着 `wants` / `missing` / `degraded` / `reason`
一起返回，设置页、`--stats`、`--selfcheck` 三处据此给出提示。
**不提示等于没做**：日文用户会看到「OCR 可用」，却拿英文模型识别中文截图，
只会以为是精度问题。

### 失败与「图里本来没字」必须可区分

两者在库里都是一条 `content=''` 的图片记录。不做区分的话，
用户搜不到字却没有任何线索（这正是本模块此前的问题）。

`OcrResult` 因此带 `error` / `error_detail`：

| error | 含义 |
| --- | --- |
| `language_unavailable` | 语言数据加载失败（由退出码 + stderr 判定） |
| `no_language_data` | 一个正文语言都没装，未调用 tesseract |
| `timeout` | 识别超时 |
| `invoke_failed` | 子进程调用失败 |
| `executable_missing` | 找不到 tesseract 可执行文件 |

判定依据是**退出码**，不是 stderr 文本 —— 空图与语言失败在 stdout 上
完全一样（都是空），只有退出码（`0` vs `1`）能分开。
关键的一点：结果在进入缓存、以及被「清空/截断」这两条路径上，
`error` 字段都必须原样保留，否则失败会被洗回「正常的空结果」。

**顺序很关键：OCR 必须排在 `PrivacyGuard.inspect()` 之前。**
因为 `inspect()` 读的就是 `item.content`，先识别再判定，
「截图里是 API Key」这种情况才会被和文本一样拦下；
反过来则会把密钥当成一张普通图片放行。

设计要点：

- **后端可插拔**（`OcrBackend` 协议）。默认给 tesseract 实现与 `NullBackend`，
  测试注入桩后端，因此**不依赖系统是否装了 tesseract**。
- **失败一律降级**。OCR 是增强能力，缺依赖或识别失败时截图照常入库，
  只是搜不到文字；`_ocr_enrich()` 里用宽泛的 `except` 兜底，不让它影响采集。
- **tesseract 调用要串行化**。它内部有共享状态、非线程安全，
  引擎里用锁保护。
- **置信度过滤**（`ocr.min_confidence`）。低置信结果往往是噪音，
  写进历史反而会污染检索，默认 0 不过滤，用户可按需调高。

## 局域网同步

`core/lan_sync.py` 与 `sync.py` 的共享文件夹模式**互补而非替代**，
两者复用同一个 `SyncRecord` 传输单元、同一个 `SyncCipher` 加密、
同一份 `PrivacyGuard` 判定，避免两条路径的过滤强度不一致。

```
A 设备                                        B 设备
┌────────────────────┐                  ┌────────────────────┐
│ LanSyncServer      │  GET /records    │ LanSyncClient      │
│  · 只提供读取       │ ◄────────────────│  · 主动拉取        │
│  · X-Linglong-Token│ since/since_id/  │  · 解密 + 导入     │
│                    │ limit            │                    │
│  · 过隐私后编码     │ ────────────────►│  · 跳过重复与敏感  │
└────────────────────┘                  └────────────────────┘
        ▲                                        │
        └──────── DiscoveryService（可选 UDP）────┘
```

几个刻意的选择：

- **拉取而非推送**。发送方不接收写入（`POST` 直接返回 405），
  攻击面只剩「读取」一条路径；接收方自己决定何时拉，不必处理对端离线队列。
- **标准库 `http.server`**。同步是几十毫秒级的小请求，
  不值得为一个功能引入 aiohttp/requests。
- **鉴权用共享口令 + 定时安全比较**。同网段不等于可信，
  请求头带上口令，服务端用 `hmac.compare_digest` 比较，避免时序侧信道；
  `/ping` 不校验口令，且只回设备名与版本，不含任何内容。
- **发现默认手动配置**。mDNS/zeroconf 要额外依赖，且不少企业 Wi-Fi 拦组播；
  UDP 广播发现作为可选项，默认关闭。
- **图片与敏感项不外发**。与共享文件夹模式一致。

`LanSync` 对外的形状（`start` / `stop` / `sync_all` / `status`）刻意与
`FolderSync` 对齐，因此 `Application.run_sync` 不需要为模式写分支。

`status()` 默认会对每个对端打一次 `/ping`（不含任何内容），
所以状态输出能给出「哪台在线、它叫什么」，而不只是一串地址 ——
此前 `probe()` 写好了却从来没人调用，`ok` / `device` 永远是空的。
`--sync-status` 因此会有约 2 秒/离线对端的等待，但不会写任何数据。

两种模式共用同一份增量游标存储（`Application.sync_cursors`），
所以切换同步模式时已同步的进度不会丢失。删除标记同理共用一份
（`Application.tombstones`），切模式时「已传播过的删除」也不会重来一遍。`sync_all()` 的 `since` 默认取
`None`，表示逐对端使用各自的持久化游标。

## 线程模型

| 线程 | 职责 | 约束 |
| --- | --- | --- |
| GUI 线程 | 所有 Qt 对象、界面刷新、剪贴板读写 | 不做耗时 I/O |
| 采集线程 | 轮询、识别、风控、落库 | 不碰任何 Qt 对象 |
| 同步线程 | 按需启动，文件读写与加解密 | 不碰 UI |
| 局域网服务线程 | `ThreadingHTTPServer`，每请求一线程 | 只读，不碰 UI |

跨线程通信只有两条通道：

- **GUI 线程 → 采集线程**：无。采集线程是只读消费者。
- **采集线程 → GUI 线程**：
  1. `GuiThreadInvoker.call()` —— 需要返回值时用（读剪贴板）
  2. `item_captured` 信号 —— 单向通知（刷新界面）

`GuiThreadInvoker` 用信号 + `threading.Event` 实现同步投递：
发起方阻塞等待，接收方在主线程执行完置位。超时 2 秒，
应用退出时 `cancel()` 唤醒所有等待者，避免采集线程死等。

## 自动化引擎

转换器是纯函数 `(text, **params) -> str | None`：

- 返回 `None` 表示「这条内容不适用该转换」，不算错误
- 抛 `TransformError` 表示「确实是错的」，错误信息直接给用户看
- 其它异常被捕获并记录，单个动作失败不影响界面

规则是数据结构而非代码，因此能从配置文件热加载，
用户可以在设置界面里改而不用重新编译。

### 三种触发时机

`Rule.trigger` 有三种取值，它们共享**同一套执行逻辑**
（`actions_for_trigger()`），只在「什么时候被调用」上不同：

| trigger | 调用点 | 产物去向 |
| --- | --- | --- |
| `auto` | `Collector.process()` 之后 | 写进记录（成为历史里的内容） |
| `outbound` | `Application.apply_outbound_rules()` | 只进这一次的剪贴板 |
| `manual` | 界面右键菜单「转换为…」 | 只进转换窗口，用户确认后才写 |

共用一个执行入口是刻意的：参数传递、链式执行、错误收集这三处若各写一份，
迟早会分叉，用户看到的现象会是「同一条规则在采集时对、在复制时不对」。

### 出站加工为什么必须单独一条通道

「复制前清理链接跟踪参数」看起来像是采集规则的另一种写法，
实际不是 —— 它改的是**即将粘贴出去的东西**，而历史里该留下的
是你原本复制的那份。所以：

- 产物**不写回存储**。`apply_outbound_rules()` 构造一份临时记录交给
  `copy_item()`，历史里的原始内容一动不动。
- 失败**静默回退**。任一步出错就照原样复制 —— 点「复制」什么都没发生，
  比「没加工」严重得多。原因收在 `OutboundData.errors` 里给界面说明。
- 隐私与出站防护**不被绕过**。敏感性按原记录判定，然后照常走
  `copy_guard.plan_outbound()` 的脱敏 / 排除系统历史 / 限时清空。

### 自我写入指纹只有一个口径

`mark_self_write()` 是「别把自己刚写出去的内容又采集回来」的机制，
它要算一个指纹，而**写的时候算一次、读的时候再算一次**。
两处口径差一个字节，标记就失效，历史里会凭空多出一条自己操作产生、
来源不明的记录。所以：

- 载荷口径由 `QtClipboardAdapter.clipboard_payload()` 单点给出。
  传的是**载荷**而不是算好的指纹 —— `mark_self_write()` 内部还要拼上类型
  再哈希一次，传指纹会被哈希两遍，又是一处对不上的口径；
- 类型一律按 `text`（写进系统剪贴板的东西就是文本），
  而不是沿用记录自己的类型 —— 从历史里复制一条 `link` 时，
  用 `link` 算指纹与读取侧的 `text` 永远对不上。

## 测试策略

| 层次 | 做法 |
| --- | --- |
| 核心逻辑 | 直接单元测试，用临时目录隔离数据 |
| 存储 | 内存/临时 SQLite，覆盖 FTS 降级与索引重建 |
| JSON 存储 | 临时目录里的 JSON 文件，覆盖损坏恢复、原子写、内联图片与搬迁 |
| 重复项合并 | 两个后端各一组同名用例：次数折算、最新时间提升、幂等、空 hash 跳过 |
| 图片附件回收 | 两个后端各一组同名用例：删除/清空/淘汰/敏感到期都收图、共享引用不误删、只碰普通 PNG |
| 平台层（Linux） | 真实调用，覆盖 X11/Wayland 双栈与降级路径 |
| 平台层（Windows/macOS） | **仿真原生层**：假的 `user32` / 假的 `Quartz`，跑真实业务链路 |
| 原生能力自检 | 自检自身可测：探测抛异常时仍要能给出结论 |
| 配置审计 | 在**假源码树**上验证判据本身：造出只声明不读取的键，审计必须报出来 |
| 配置迁移 | 注册一档假迁移，验证它被执行、失败时保留原配置、更高版本被放过 |
| 界面 | Qt `offscreen` 平台，无需显示器，CI 可跑 |
| 端到端 | 真实 Qt 剪贴板 → 采集 → 落库 → 检索 → 变换 → 写回 |

平台原生代码（Windows/macOS）在 Linux CI 上无法执行，最初的做法是
「把能力探测与能力使用分开，使用逻辑用桩对象验契约」。这个做法有个盲区：
**它只能验「调用了某个方法」，不能验「事件真的走到了回调」**。
实测中它漏掉了两个缺陷：macOS 后端 `is_available` 返回真但 `register()`
是空实现；Windows 侧 `RegisterHotKey` 成功但 `WM_HOTKEY` 没人分发。

现在的做法是**仿真原生层**：

```python
# 喂一个假的 user32，然后走真实的 register() → 事件 → 回调
win_backend.register(5, "Ctrl+Shift+V", lambda: fired.append("hit"))
win_backend.handle_native_event(0, SimpleNamespace(message=WM_HOTKEY, wParam=5))
assert fired == ["hit"]        # 打桩式测试永远发现不了这一条
```

`tests/test_hotkeys.py`（50 个用例）覆盖：Windows 修饰键位与虚拟键码映射、
`WM_HOTKEY` 分发、未知 id 不误触发、回调异常不拖垮消息循环；
macOS 权限未授予、tap 创建失败、事件标志位精确匹配（多按修饰键不触发、
CapsLock 不影响）、系统超时停掉 tap 后自动重开。

仿真的边界要说清：**真实的键码冲突、权限弹窗、系统消息投递时序仍然验不到**。
这些只能靠 `tools/native_check.py` 在真机上跑一遍，
清单见 `docs/native-verification.md`。

### 「空转配置」为什么测不出来

一个配置项如果没有读取方，就**没有可断言的行为** —— 测试写无可写。
所以这一类的守卫不是行为测试，而是静态审计（`--config-audit`）。
审计本身也有测试：在临时目录里造一个假源码树，里面放一个只被声明、
没有任何读取方的键，断言审计能报出来；再放一个真被读的键，断言不被误报。

判据的两端都要有守卫：

- 「同段里别的键被读了 ⇒ 这个键也有人读」必须**不成立**
  （否则最常见的空转形态全被漏掉）
- 「父级键被整体取用 ⇒ 该段是动态读取」必须**成立**
  （否则 `config.get("ocr." + name)` 这类会误报）

这类缺陷的共同点是**靠读代码发现，跑测试发现不了**，
所以工具本身得进 CI —— 否则它自己就成了下一个「声明了但没人用」。
